# Энергоэкспортёры (прод, партнёрская ветка)

Манифесты-заготовки для фазы P0 энерговетки
([[Энергоэффективность]]): съём наземной энергии с PDU (SNMP)
и мощности через BMC (IPMI). **В kustomization НЕ включены** — сознательно:
оба требуют партнёрских данных (чек-лист Д1–Д4 плана), которых пока нет, а
полуслепой конфиг в базовом стеке дал бы вечно красные таргеты Prometheus.

Порядок включения на проде (фаза P0):

1. Получить от партнёра: модель PDU + SNMP-креды (Д1–Д2), карту
   розетка↔узел (Д3). ~~Креды BMC (Д4)~~ — получены 18.08.2026.
2. **Мощность BMC снимается (18.08.2026), с 19.08 — ИЗ КЛАСТЕРА.** Партнёр
   открыл VM-сетям доступ к iDRAC-сети (tcp/443) — лаба исключена из
   энергосхемы: тот же `scripts/idrac-power-poller.py` теперь крутится
   Deployment'ом `idrac-poller` на ss-system (манифест в base;
   `make energy-idrac-deploy` собирает ConfigMap из scripts/ и требует
   Secret `idrac-credentials`) и толкает в pushgateway по ClusterIP.
   Метрики прежние: `idrac_power_watts`, `idrac_psu_input_watts`,
   `idrac_poll_timestamp_seconds`. Лабный юнит `ss-idrac-poller` погашен и
   удалён 19.08 (карта узел→BMC жила и в юните, и в манифесте — два источника
   правды об одном; остался манифест). `ss-forward@pushgateway` НЕ выведен:
   его клиентом стал маркер серии из run-series.sh. Заготовка `ipmi-exporter.yaml`
   остаётся перекрытой poller'ом. Накопительного счётчика энергии у iDRAC
   этой прошивки нет — источник ipmi в energy_windows будет интегрированием
   опроса (Э0.1 — по средней мощности, этого достаточно).
3. Для PDU: заготовка `snmp-exporter.yaml` **конкретизирована 19.08.2026**
   под AP8853 — рукописный модуль rPDU2 (мощность/энергия устройства, токи
   фаз и банков; OID сверить snmpwalk'ом при первом подключении — единицы
   там сотые кВт / десятые кВт·ч / десятые ампера, потребителю нужен
   `--pdu-factor 3.6e5`), community — из Secret `snmp-exporter-auth`
   вторым конфиг-файлом (рецепт в шапке yaml). Осталось при подключении:
   вписать IP обеих PDU в scrape-снипет (метка pdu: a/b), создать секрет,
   добавить файл в overlay и джоб в prometheus-configmap.

   **Модель известна (19.08.2026): APC AP8853, Rack PDU 2G METERED, Zero U**
   — однофазная 32А, 2 банка по 16А, 36×C13 + 6×C19, Ethernet 10/100
   (web/SSH/Telnet/SNMP), каскадирование до 4 шт. под одним IP. Ключевое
   ограничение: **Metered = учёт по входу и по банкам, ПО-РОЗЕТОЧНОГО учёта
   НЕТ** (это AP84xx/86xx Metered-by-Outlet или AP89xx Switched) и
   управления розетками нет. Следствия для плана: PDU-член цепочки Э0.4 —
   агрегат стойки (или банка), не пер-узловой; кросс-валидация P0 — на
   уровне суммы трёх узлов, и чистота зависит от того, кто ещё воткнут в
   те же банки. SNMP (PowerNet-MIB, rPDU2): мощность устройства (Вт), токи
   фазы/банков (0.1А), накопительный счётчик энергии устройства (kWh,
   шаг 0.1 kWh = 360 кДж — годится для длинных окон, для короткого окна —
   интегрирование опроса мощности). Осталось получить от партнёра:
   **IP PDU** (и виден ли он из VM-сетей, как iDRAC), **SNMP read-only
   community** (или создать), **карту розеток**: какие розетки/банки заняты
   PS1 И PS2 каждого из wrk-b6/b7/b8 (у PS2 дежурка ~5 Вт — суммировать оба
   входа), **кто ещё запитан от тех же банков** (чистота агрегата), и есть
   ли каскад (Network Port Sharing меняет адресацию юнитов в SNMP).

   **Уточнение партнёра 19.08:** PDU в стойке ДВЕ (обе AP8853), сервера
   подключены к обеим — классическая A/B-схема: PS1 узла в одну, PS2 в
   другую. Следствия: (1) полная мощность узлов = СУММА двух PDU (PS2 в
   дежурке ~5 Вт, но Dell умеет перекидывать нагрузку между БП — одну PDU
   игнорировать нельзя); (2) в Prometheus нужны обе как отдельные цели с
   лейблом pdu (или каскад под одним IP — уточнить при подключении);
   (3) карта розеток нужна ПО КАЖДОЙ PDU. Сетевые интерфейсы PDU пока
   никуда не подключены — партнёр занимается 20.08; до тех пор Д2/Д3
   заморожены, наша сторона готова (snmp-exporter заготовка).
4. Кросс-валидация PDU↔RAPL↔IPMI по плану P0. **RAPL снимает metrics-agent
   (решено и реализовано 18.08.2026)** — вариант «а» из прежней развилки:
   агент и так единственный разрешённый постоянный процесс на bench-узлах,
   RAPL в нём не приводит на узел ничего нового. Реализация: `pkg/rapl`
   (обход powercap-зон, коррекция переполнения по `max_energy_range_uj`,
   mmio-дубли исключены) → `ss_node_rapl_joules_total{zone,domain}` +
   `ss_agent_rapl_zones` в `/metrics` агента; хостовый /sys смонтирован
   ro (runc маскирует контейнерный powercap после PLATYPUS), агент работает
   root'ом — права на `energy_uj` (0400 root) есть. На ВМ (ss-system,
   STAGE) зон нет — `ss_agent_rapl_zones=0`, метрики честно отсутствуют
   (RAPL в виртуалке и был бы недостоверен). Проверено на wrk-b6: 5 зон —
   2× package + 2× dram + **psys** (полноплатформенный домен, бонус для
   Э0.2). PMU-прогноз A5 не задет: чтение energy_uj — MSR-backed sysfs,
   не perf-события.

   Отклонённые варианты (для истории): node-exporter на bench с
   `--collector.rapl` (посторонний процесс — нарушение чистоты; и в базовом
   стеке он под uid 65534 — energy_uj не прочитал бы) и отказ от RAPL в
   пользу одного PDU (теряется пофакторная атрибуция узел↔сокет).

Съём энергии окна в ClickHouse — `scripts/energy-window.py` (границы окна →
разность накопительного счётчика → sensitivityscore.energy_windows,
миграция 003).

## Прототип: remote_write → ClickHouse TimeSeries (лаба, 20.08.2026)

`ch-timeseries-proto.yaml` — неймспейс `ts-proto` на local72: отдельный CH
26.7 с экспериментальным движком TimeSeries + миниатюрный Prometheus,
пишущий в него remote_write'ом (самоскрейп как источник рядов). Итоги
обкатки:

- пишет и читается: ~250 метрик, SQL через `timeSeriesData()/-Tags()/-Metrics()`;
- **переживает рестарт CH без потерь**: hostPath держит данные, а
  Prometheus дослал из WAL всё накопленное за простой приёмника — дыры нет;
- хранение ~6 Б/сэмпл до мерджей — для энергометрик прода пренебрежимо;
- грабли: (1) движок за флагом `allow_experimental_time_series_table`;
  (2) пользователь `default` образа заперт на localhost — remote_write
  нужен отдельный пользователь (заголовок `X-ClickHouse-User`).

Вывод для прода: Prometheus остаётся скрейп/алерт-слоем, remote_write в
CH добавляется как долговечный архив сырых рядов (провенанс чисел статьи).
Решение об интеграции — после Ш-фаз; на прод этот манифест не применять.
Снос прототипа: `kubectl delete ns ts-proto` + `/var/lib/ch-ts-proto` на узле.
