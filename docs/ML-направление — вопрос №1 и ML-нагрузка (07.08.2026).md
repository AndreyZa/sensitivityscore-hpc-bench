## 1. ML-вопрос №1: GBDT vs линейная модель цены осей — ЗАМЕРЕНО

**Постановка.** Линейная калибровка (`calibrate_axis_costs.py`) — регрессия с
ручными взаимодействиями p·s. Даёт ли следующая ступень ёмкости (градиентный
бустинг, взаимодействия учит сам) меньшую out-of-sample ошибку на тех же
данных и том же информационном наборе? Скрипт: `analysis/ml_slowdown.py`
(`make ml-slowdown` поверх ch-tunnel).

**Честность:** датасет собран функциями калибровочного скрипта (серии LLC +
смешанная, y = slowdown−1, **N=360 строк** — выборка калибровки, не все 3.5k
строк CH); GBDT получает сомножители (p, s), а не произведения; обе модели
переобучаются в каждом фолде; фолды — GroupKFold по (серия, повтор), чтобы не
протечь псевдорепликацией; ΔMAE — парный кластерный бутстреп по 20 группам.

**Результат (out-of-fold, seed 20260807):**

| модель | MAE | RMSE |
|---|---|---|
| наивная (среднее трейна) | 0.0824 | 0.1018 |
| линейная (NNLS, p·s) | 0.0455 | 0.0594 |
| GBDT (p, s) | 0.0420 | 0.0557 |

ΔMAE (GBDT − линейная) = **−0.0035, 95% ДИ [−0.0062; −0.0010]** — ДИ не
накрывает ноль; сиды 1 и 42 дают −0.0024…−0.0034 с тем же знаком.

**Чтение двустороннее, и оба чтения полезны диссертации:**
- линейная модель забирает **~91%** достижимого улучшения над наивной
  (0.0824→0.0455 из возможных →0.0420) — интерпретируемый бейзлайн сильный,
  цены осей с ДИ остаются главным носителем смысла;
- GBDT статистически значимо добирает **~8% MAE** уже на N=360 — сигнал
  нелинейности/невыраженных взаимодействий существует. На прод-данных
  (скученность node_capacity_jobs≥2, NUMA, кросс-термы LLC×NUMA) вопрос
  ставится заново и острее.

**Рамка для главы:** потолок выигрыша любого более умного скоринга ограничен
регретом линейного против оракула (на STAGE mixed-calib — 0.03). Лучший
предсказатель ≠ лучшее размещение: решает граница arg-max, а не RMSE.
Измерить регрет на проде → станет ясно, есть ли ML-скорингу что выигрывать.

## 2. ML-нагрузка как workload

**Что переносится:** оси (LLC/membw — боль CPU-инференса, net — allreduce
распределённого обучения, io — data pipeline), декларация S (training =
net+io-high, инференс = llc-high), весь протокол валидации (близнецы, штормы,
per-node baselines, regret). Прод-Xeon 8462Y+ несёт AMX — CPU-инференс там
первосортный гражданин.

**Что меняется:** метрика (сервис живёт в p95/throughput при SLO, не в
makespan; у батч-инференса фиксированного объёма makespan остаётся честным);
долгоживущесть (сервис = генератор нагрузки на T секунд); решение метода —
только при размещении (миграция — за границей метода, оговорить).

### Пилот на STAGE 07.08 — различимость осей инференс-жертвой

Методика: под `python:3.12-slim` на bench-узле `w8` (квота 500m/1Gi — как у
жертв серий), ResNet50 v1-12 ONNX fp32, batch=1, 1 поток; N=150 инференсов на
повтор, 3 повтора на фазу, один тёплый под на все фазы (exec). Агрессоры —
штатный образ `andreyza/aggressor:dev` с заявками-невидимками (10m/32Mi).
Вход детерминирован — изменчивость только от среды.

| фаза | медиана inf/s | p50, мс | p95, мс |
|---|---|---|---|
| A — соло | 5.52 | 189.5 | 197.5 |
| B — membw-шторм (`--stream 2`) | 5.23 (**−5.2%**) | 194.1 | 210.2 (**+6.4%**) |
| C — дисковый шторм (`--hdd 2`, плацебо) | 5.41 (−1.8%) | 190.3 | 207.8 |

Повторы внутри фаз стабильны (A: 5.508–5.556). Порядок B < C < A без
пересечений по throughput.

**Выводы пилота.**
1. Инференс-жертва **различает оси** даже в худших для LLC-сигнала условиях
   (KVM, квота 500m, виртуальный PMU — то, из-за чего cˢ_llc прод-гейтед):
   membw-шторм бьёт втрое сильнее дискового; p50 под диском вообще не
   двигается (хвост p95 — общий узел, ожидаемо).
2. **Механика прод-профиля валидирована**: рантайм ставится pip'ом в под,
   модель 102 МБ тянется в контейнер, повторы стабильны, батч-инференс
   фиксированного N ложится в makespan-модель харнесса **без изменения
   схемы данных** (total_s ≡ makespan). Перцентили латентности — расширение
   (лог/колонка), не условие первой серии.
3. Данные пилота в CH не заливались (ручная разведка, не серия); кластер
   после пилота чист.

Скрипт пробы (для воспроизведения / основы прод-образа):

```python
# ml_probe.py — батч-инференс ResNet50 (ONNX, fp32, batch=1) фикс. числом
# запросов; JSON с throughput и перцентилями. Вход детерминирован (seed 0).
import json, os, time
import numpy as np
import onnxruntime as ort

N = int(os.environ.get("N_INFER", "150"))
WARMUP = int(os.environ.get("N_WARMUP", "5"))
so = ort.SessionOptions()
so.intra_op_num_threads = int(os.environ.get("ORT_THREADS", "1"))
so.inter_op_num_threads = 1
sess = ort.InferenceSession("/model.onnx", so, providers=["CPUExecutionProvider"])
inp = sess.get_inputs()[0]
shape = [d if isinstance(d, int) else 1 for d in inp.shape]
x = np.random.default_rng(0).standard_normal(shape).astype(np.float32)
for _ in range(WARMUP):
    sess.run(None, {inp.name: x})
lat = []
t0 = time.monotonic()
for _ in range(N):
    t = time.monotonic()
    sess.run(None, {inp.name: x})
    lat.append(time.monotonic() - t)
total = time.monotonic() - t0
ms = sorted(v * 1000 for v in lat)
q = lambda p: ms[min(len(ms) - 1, int(p * len(ms)))]
print(json.dumps({"n": N, "total_s": round(total, 2),
                  "inf_per_s": round(N / total, 3), "p50_ms": round(q(0.5), 1),
                  "p95_ms": round(q(0.95), 1), "max_ms": round(ms[-1], 1)}))
```

(Модель: `onnx/models` → `validated/vision/classification/resnet/model/
resnet50-v1-12.onnx`; фазы — соло / `--stream 2` / `--hdd 2 --hdd-bytes 1g`
на узле жертвы.)
