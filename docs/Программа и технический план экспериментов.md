# Программа и технический план экспериментов (Geant4)

*PhD · Главы 1–4.* Сравнение архитектур планирования HPC-нагрузки: K8s
bare-metal (A), K8s+KubeVirt (B), Slurm (C), Slinky/slurm-bridge (D).
19.08.2026 объединил и сократил два прежних документа — «Программа
экспериментов (Geant4)» (партнёрско-научная рамка) и «Технический план
экспериментов» (реализация); история — в git.

Цель — количественно подтвердить/опровергнуть гипотезу: job-level, NUMA- и
cache-aware планирование (SensitivityScore) даёт измеримое преимущество по
makespan и стабильности против (а) generic-планировщиков K8s, (б) Slurm,
(в) гибридных схем K8s+Slurm.

---

## 1. Нагрузка: Geant4 и параметризация профиля S

Geant4 (Монте-Карло симуляция частиц; класс Particle Methods по Berkeley
«13 Dwarfs», как LAMMPS) выбран за профиль, отображающийся на вектор
S = {LLC, NUMA, Net, IO}: нерегулярный доступ к таблицам сечений (LLC),
общие read-only таблицы MT-потоков (NUMA), всплесковая сеть, управляемый
вывод (IO). Образ — `examples/extended` TestEm5 (своё приложение не нужно),
multistage build, `andreyza/geant4:11.2`.

**Центральная идея: один бинарник — разные профили интерференции**, через
env (`workload/entrypoint.sh`):

| Параметр | Low-S | High-S | Влияет на |
|---|---|---|---|
| `G4_THREADS` | 1 | ядра NUMA-домена (28–32 на проде) | NUMA remote ratio |
| `PHYSICS_LIST` | QGSP_BERT | FTFP_BERT_HP | ~~LLC working set~~ **не работает: TestEm5 игнорирует PHYSLIST** (свой ЭМ-список; найдено 19.08.2026, см. harness/profiles.py). Физика всех серий одинаковая; llc/membw-жертву даёт ML-профиль (рекалибровка v2) |
| `N_PRIMARIES` | 10⁴ | 10⁶–10⁷ (прод: 60–75M ≈ 4–5 мин) | длительность, стабильность |
| `OUTPUT_MODE` | none | `blocking` — запись на критическом пути; `stream` — то же по сети на приёмник; `burst` — фоновый писатель (только детекция) | IO / Net |
| `RNG_SEED` | фиксирован на повтор | — | воспроизводимость |

Профиль декларируется аннотациями (`scheduling.phd/sensitivity-{llc,numa,net,io}:
high|medium|low` + `job-id` для корреляции с метриками в Redis).

## 2. Конфигурации стенда

| Конфигурация | Планирование | Изоляция | Назначение |
|---|---|---|---|
| **A. K8s bare-metal** | default vs SensitivityScore | cgroups/контейнер | прямое A/B-сравнение плагина |
| **B. K8s + KubeVirt** | те же над VMI | QEMU/KVM поверх пода | применимость в VM-кластерах; цена виртуализации для S-метрик |
| **C. Slurm** | Slurm controller | whole-node | эталон HPC «как есть» |
| **D. Slinky (slurm-bridge)** | Slurm как K8s-планировщик | под K8s → Slurm job | ближайший production-аналог гибрида |

**Slinky** (SchedMD + NVIDIA): slurm-operator (Slurm внутри K8s) +
slurm-bridge (делегирует выбор узла контроллеру Slurm). Прямой аналог
архитектурной идеи диссертации (job-level связь оркестрации и
планирования), но **без модели Z = {G, R, S} и без чувствительности к
LLC/NUMA/IO** — решение принимает классический Slurm по своим политикам.
Усиливает новизну: организационное разделение ресурсов против модели
интерференции. Ограничения: K8s ≥ 1.35 (пройден: k0s v1.35.6) + Slurm ≥
25.11; **аллокации whole-node** — co-location разных чувствительностей на
одном узле тестируем только на A/B; DRA-драйверы ограничены.

## 3. Метрики и связь с вектором S

| Ось | Метрика | Источник | В score? |
|---|---|---|---|
| LLC | узел: промахи/с к `LLC_REFERENCE_MISSES_PER_SEC`¹; задача: miss ratio | PMU, cgroup-scoped | да |
| NUMA | `remote / (local + remote)` = `node-load-misses / (node-loads + node-load-misses)`³ | PMU, generic NODE-события | да |
| Net | `net_pressure = net_bw / NET_REFERENCE_MBPS` (+ сырой net_bw) | `/proc/<pid>/net/dev` (hostPID) | да² |
| IO | `io_pressure` (PSI, [0,1]) + сырые `io_iops` | cgroup v2 `io.pressure` / `io.stat` | да (PSI) |
| Интегральные | makespan, slowdown, placement regret, throughput | terminated-времена / sacct / снапшот давления | — |

¹ Для узла — промахи/сек, не отношение: под потоковой нагрузкой знаменатель
растёт быстрее числителя, и загруженный узел выглядел бы чище простаивающего.
² Без референса `net_pressure = 0` — ось выключена честно; референс — НЕ
номинал NIC (из-под CNI не читается; same-node мостится veth), а
эмпирический cross-node `iperf3 --bidir` → ConfigMap
`metrics-agent-calibration` (механика и значения прода — «Прод-стенд.md»
§2, §5).
³ С 18.08.2026: на современных Intel generic node-события ДИЗЪЮНКТНЫ
(`node-loads` — только локальные DRAM-чтения, `node-load-misses` — только
удалённые); старая формула `misses/loads` на любом удалённом трафике
превышала 1 и клампилась. С 19.08 — гейт знаменателя
`NUMA_MIN_DRAM_EVENTS_PER_SEC` (кэш-резидентные жертвы дают мусорные
доли на ~7К соб/с). Детали — `metrics-agent/pkg/perf/sampler.go`, Методика.

**PMU внутри VM (конфигурация B) — ключевой риск серии B:** KVM/QEMU по
умолчанию не пробрасывает PMU гостю; vPMU passthrough требует поддержки и
снижает миграцию/плотность. Решение первой итерации: собирать LLC/NUMA
host-side по cgroup процесса `qemu-kvm` (резолвер VMI → PID → cgroup),
помечая прогоны `approximation: host-side`; health-check при старте серии B
переключает на in-guest сбор, если vPMU есть. «Виртуализация ⇒ нет PMU»
неверно в общем случае — зависит от гипервизора (Timeweb KVM считал
cgroup-PMU честно, VMware Workstation — нулём), поэтому perfcheck гоняется
поузлово. Исторический урок: cgroup-события требуют `cpu >= 0` — годами
списывали `EINVAL` на гипервизоры, а это был наш баг открытия счётчика.

## 4. Гипотезы и статус

> Статус по итогам десяти серий STAGE (июль 2026): **H1 подтверждена** (по
> метрикам решения и — после уточнения модели базовой ценой оси — по
> времени); различение по чувствительности (cˢ > 0) доказано близнецами:
> диск ×1.73 [1.65; 1.84] p=0.008, сеть ×6.22 [5.66; 6.82] p=0.002
> (повтор с нейтральным приёмником ×4.20 [3.96; 5.33] p=0.004) —
> `analysis/twin_contrast.py`. **H1-trimaran подтверждена.** H2–H4 ждут
> конфигураций B/C/D. Числа — «Сводка результатов STAGE (июль 2026)».

- **H1** — SensitivityScore (A) даёт меньший makespan и дисперсию против
  default при co-location high-S и low-S задач.
- **H1-trimaran** (контроль) — преимущество даёт именно вектор S, а не
  «любой учёт загрузки»: обыгрыш load-aware Trimaran LVRB (слеп к
  LLC/NUMA/IO; агрессор с малым cpu-request невидим и для requests, и для
  утилизации) отделяет interference-awareness от load-awareness.
- **H2** — виртуализация (B) снижает эффективность, но относительное
  преимущество над default внутри B сохраняется (эффект аддитивен).
- **H3** — Slurm (C) быстрее на однородной нагрузке, но проигрывает в
  сценариях co-location с интерференцией (не в чистом batch).
- **H4** — Slinky (D) ≈ C на однородной, но проигрывает A на смешанной
  чувствительности — эмпирическое подтверждение новизны.

**План:** независимые — конфигурация A–D × профиль (low-S / high-S) ×
overcommit (1.0 / 1.5 / 2.0); зависимые — makespan (медиана, p95),
slowdown (= makespan / соло-бейзлайн), placement regret, оси S, CV;
контроль — фиксированные версии Geant4/стека, ≥ 10 повторов на точку,
прогрев узлов.

## 5. Скор-функция и плагин

Исходная форма — скалярное произведение профиля задачи и давления узла:
`interference = dot(S_job, Pressure_node)`, score = normalize(max −
interference·weight); веса — в ConfigMap (абляция оси = нули).

**Уточнение по калибровке STAGE (14.07.2026), форма сохранена:** чистый
dot-product предполагал, что за давление платит только чувствительная
задача — калибровка по 360 задачам опровергла (у дисковой оси цена
*базовая*: +24 % ЛЮБОЙ задаче узла при давлении 1.0):

```
вклад оси = давление · (base + sensitivity · s_job)
score     = 100 − 100 · Σ вклад / Σ (base + sensitivity)
```

`weights.json = {"base": {…}, "sensitivity": {…}}` (плоский старый формат
читается как sensitivity с base=0). Значения — эмпирическая калибровка
стенда (`analysis/calibrate_axis_costs.py`; прод-числа 19.08 — β_io=1.31,
см. «Прод-стенд.md» §7): нормируется не измерение давления, а его
*стоимость*. Для конфигурации B источник Pressure — интерфейс
`NodeStateResolver` (PodCgroupResolver / QemuProcessResolver).

## 6. Агент метрик

DaemonSet (Go), `CAP_PERFMON` + SYS_PTRACE — не полный privileged
(аргумент безопасности в защите). LLC/NUMA — честные PMU-счётчики
cgroup-scoped `perf_event_open()`; Net/IO — из cgroup v2 и netns пода
(источники не смешиваются, нормализуются в единый PressureVector).

Redis: `node:metrics:<node>` (hot-path планировщика, TTL 30с) +
`job:metrics:<job_id>:<node>` (история для анализа: суммы + счётчик,
харнесс делит — lifetime mean). Контракт полей — `contract/redis-fields.yaml`,
целостность проверяет preflight серии.

## 7. Харнесс

`harness/run_experiment.py`, три взаимоисключающих режима:
1. **матрица** — конфигурация × профиль × overcommit × повторы; overcommit
   переводится в РЕАЛЬНОЕ число одновременных job
   (`batch_size = round(node_capacity_jobs × overcommit)`) — иначе
   co-location не создаётся и H1 не проверяется;
2. **`--pressure`** («money experiment») — фоновые агрессоры на части нод
   (nodeName-пин мимо планировщиков, малый cpu-request — невидимы для
   ресурсной модели) + поток жертв через планировщик каждого плеча;
3. **`--baseline`** — соло-прогоны на пустом кластере (знаменатели
   slowdown + fingerprint-эталон).

Ветки сабмита: A/B — манифест из шаблона + `kubectl wait`; C — `sbatch
--export=`, makespan из `sacct Elapsed`; D — манифесты A через
slurm-bridge, makespan с обеих сторон (оверхед трансляции — отдельная
метрика). Плечи задаёт `scheduler_variants`
(default/sensitivityscore/trimaran/…).

## 8. Данные и анализ

Схема (Parquet):

```
config | profile | overcommit | rep | node | makespan_s | makespan_source |
submit_ts | start_ts | end_ts | llc_miss_rate | numa_remote_ratio | net_bw |
io_iops | io_pressure | approximation | scenario | batch_size | batch_index |
interference_chosen | placement_regret | sensitivity_{llc,numa,net,io}
```

- `makespan_s` — чистое время исполнения (`startedAt→finishedAt`
  контейнера / `sacct Elapsed`) — исключает очередь и пулл, K8s и Slurm
  сравнимы напрямую; `makespan_source` = container | sacct | wallclock.
- `scenario` = batch | pressure:<name> | baseline — анализ НЕ смешивает их
  в одну группу (разные оси overcommit).
- `placement_regret` = interference(выбранный узел) − min по узлам, той же
  скор-функцией, считает харнесс — покрыто и плечо A-default.

**Статистика:** одна репликация = один объект (среднее по батчу — члены
батча со-размещены намеренно и не независимы, иначе p переуверен);
Mann-Whitney U (10 повторов, нет оснований для нормальности,
правые хвосты); Holm-Bonferroni на семейство (пара сценарий×метрика — своя
семья), вердикты из `mw_p_holm`; эффект — Cliff's delta; стабильность —
CV = σ/μ (не голая σ: плечи разные по абсолютному makespan). Свип по трём
метрикам «меньше = лучше»: makespan, slowdown, placement_regret (последний
— только где есть внешнее давление на момент сабмита).

**Визуализация:** boxplot makespan по config×profile при overcommit 2.0;
scatter «ось S vs makespan» (обоснование оси как измерения); boxplot
regret по плечам (график механизма); CV-сравнение; fingerprint-таблица
«заявленный vs измеренный S» + монотонность (high обязан мериться выше
low).
