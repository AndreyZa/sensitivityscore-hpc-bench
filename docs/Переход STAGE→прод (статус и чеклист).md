## 3. ПРОД — на следующей неделе (готовность и что нужно для старта)

### 3.1 Готово
- **Провижнер** (`hpc-k0s-provision`): Ansible (OS-prep) + k0sctl (HA 3-CP + 3×
  R760 + ss-system), кнопка `make provision`, CI/линт зелёные, validated `--check`.
- **Топология зафиксирована:** 3× Dell R760 (2× Xeon 8462Y+, 64c/128t, **2 NUMA
  домена**, 384 ГБ, bare-metal) = bench-узлы; 4 служебные ВМ на отдельном
  гипервизоре (3 CP + 1 ss-system с Redis/scheduler/metrics-server/CH).
- **Прод-гейтед пункты разблокируются железом:** NUMA-ось активируется (2
  домена), честный PMU (bare-metal), полные ядра → **β>0** (различение задач по
  чувствительности) и **cˢ_llc** становятся измеримы.

### 3.2 Нужно для старта (чеклист ввода)
1. **Заполнить IP** в `inventory/hosts.yml` провижнера (7 хостов) → `make provision`.
2. **Три калибровки на новом стенде** (без них «выводы о времени делать нельзя»):
   опорные значения осей (LLC misses/s, NET Mbps, IO PSI) + **цены осей**
   `calibrate_axis_costs.py` → `weights.json {base,sensitivity}`.
3. **Same-session per-node baselines** (урок STAGE: дрейф ДЦ — крупнейший член).
4. **Смоук-серия** + проверка предрегистрированного **прогноза A5** (EPYC→Xeon
   поправка учтена: L3 socket-wide, NUMA активна).
5. **CH — РЕШЕНО (06.08): .72 остаётся первичным, ДУБЛИРУЕТСЯ in-cluster.**
   Агрегатор на .72 живёт как есть (первичный, отчёты/сверки из него). На прод
   ss-system поднять in-cluster CH как дубль: (а) засеять историю STAGE из
   бэкапа (`sensitivityscore-ch-backup-<дата>.tar.gz` → `restore.sh`), (б) далее
   дублировать запись — `make ch-load-all CH_SINKS="prod home"` (parquet →
   оба приёмника, устойчиво к падению одного) либо синхронизация. Прод-серии
   идут в оба. Итог: две живые копии, .72 — источник правды, in-cluster —
   прод-локальная.
   - **ВАЛИДИРОВАНО на STAGE 06.08 (пока стенд жив):** манифест
     `k8s/clickhouse/base` развёрнут (`make ch-incluster-deploy`) — StatefulSet
     CH 25.3, PVC 5Gi (local-path), schema-Job, Service — всё поднялось на
     ss-system узле. Засев из бэкапа (шаг «а») через `restore.sh` дал **точную
     копию .72**: строки 3530/459, 31 метка, ключевые агрегаты совпали побайтно
     (mixed-calib SS 78.82, net-diff-v2 SS медиана 53). Путь «бэкап→restore→
     in-cluster» и деплой-манифест на проде проверены.
   - **Шаг «б» ТОЖЕ валидирован на STAGE 06.08:** минимальная smoke-серия
     (`make series`, 1 плечо/1 жертва/1 повтор) → parquet → `ch-load-all
     CH_SINKS="prod home"` залил в оба CH; метка совпала побайтно (содержимое +
     провенанс). Заодно проверена операционная цепочка запуска (preflight →
     baseline+pressure → parquet). Всё убрано, STAGE восстановлен (метка снята
     из обоих CH, .72 снова 31 метка, bench-ns пуст).
   - **Заметки для прод-деплоя CH (из обкатки):** (1) деплоить ТОЛЬКО оверлеем
     `CH_KUSTOMIZE=k8s/clickhouse/overlays/prod` — `base` без nodeSelector, CH
     сядет на измерительный узел и preflight его завалит; оверлей пинит к роли
     `node-role.kubernetes.io/ss-system`+toleration (проверено — сел на .5).
     (2) ~~пробел с schema-Job~~ ЗАКРЫТ 07.08: оверлей теперь пинит и Job
     (`job-placement-patch.yaml`), на bench-узлы ничего из CH не садится.
