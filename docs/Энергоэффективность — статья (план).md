# Энергоэффективность — отдельная ветка (Peaks), план статьи

Составлен 17.08.2026, уточнён в тот же день: по решению партнёров это
**самостоятельное направление, не завязанное на SensitivityScore**. Ядро —
энергоосознанное размещение готовыми средствами экосистемы, в первую очередь
**Trimaran Peaks** (жадный выбор узла по предельной мощности, модель
P(x) = K0 + K1·e^(K2·x)); SS в этой ветке не участвует — связь двух
направлений упомянута единственной строкой в конце как перспектива.

От SS-энергоплана ([[Энергоэффективность (план, прод)]]) переиспользуется
только **инструментовка и дисциплина** (PDU/RAPL/IPMI, предрегистрация,
ClickHouse как точка правды, бутстреп по повторениям) — она планировщик-
агностична. Гипотезы H1–H4 того плана остаются в SS-ветке и здесь не нужны.

---

## 0. Почему это статья, а не просто внедрение

Peaks в экосистеме есть, но эмпирики по нему почти нет: публикаций с
**наземным** (PDU) замером экономии на bare-metal — единицы, калибровка его
модели мощности на конкретном железе нигде не описана как воспроизводимая
процедура. Вклад ветки:

1. **Воспроизводимая калибровка** модели P(x) = K0 + K1·e^(K2·x) для
   современного серверного железа (Sapphire Rapids) с наземной валидацией
   предсказаний по PDU.
2. **Честное измерение экономии по полному циклу**: сам Peaks лишь
   концентрирует нагрузку — ватты экономятся, когда освобождённый узел
   реально гасится. Меряем обе половины отдельно (это главный ожидаемый
   результат: без гашения экономия мала).
3. **Методика**: предрегистрация числовых прогнозов, парный дизайн,
   Дж/задача и EDP, кластерный бутстреп — перенос дисциплины статьи №1 на
   энергодомен.

## 1. Тесты по энергопотреблению и доступ к железу

### Факты

- Прод-стенд: **3× Dell PowerEdge R760** — 2× Intel Xeon Platinum 8462Y+
  (Sapphire Rapids), 64 ядра / 128 потоков, 2 NUMA-домена, 384 ГБ RAM,
  bare-metal ([[Ввод прод-стенда (Этап 0)]] §4). RAPL и BMC доступны по
  построению; на STAGE (KVM) энергетика невыполнима — гейт прод.
- **PDU предоставляет партнёр** (решение 06.08).
- **Peaks уже в нашем бинаре**: форк содержит `pkg/trimaran/peaks`
  апстрима, образ собирается CI форка; включение — профиль
  KubeSchedulerConfiguration с плагином Peaks и `NodePowerModel`
  (JSON per-node, K0/K1/K2). load-watcher уже развёрнут (нужен
  Trimaran-контролю в основных сериях).
- Гашение узлов на bare-metal — через BMC: `ipmitool power off/on`
  (cordon + drain перед гашением); автоматизация сценарием серии,
  контроллер не требуется.

### Чек-лист доступа — запросить у партнёра ДО начала (общий с SS-веткой)

| # | Что нужно | Зачем | Статус |
|---|---|---|---|
| Д1 | Модель PDU, per-outlet metering, накопительный регистр кВт·ч | наземная истина | ждём |
| Д2 | SNMP/REST доступ к PDU (креды, OID) | snmp_exporter → Prometheus | ждём |
| Д3 | Карта розетка ↔ узел (обе розетки при двойных PSU) | атрибуция | при монтаже |
| Д4 | Доступ к BMC (IPMI/Redfish): power reading **и power control** | сверка мощности + гашение узлов | запросить |
| Д5 | Root на узлах: powercap sysfs (RAPL), governor | атрибуция, контроль DVFS | с вводом стенда |
| Д6 | PTP/дисциплинированный NTP | сведение окон энергии с epoch'ами | уточнить |
| Д7 | Окно полного простоя (часы) | idle- и suspend-калибровка | согласовать |
| Д8 | Тариф (день/ночь/пик), PUE, фактор CO₂ | перевод в деньги | входы партнёра |

Отличие от SS-ветки одно: в Д4 нужен ещё и **power control** (гашение), не
только чтение.

### Фазы экспериментов

| Фаза | Что делаем | Что даёт |
|---|---|---|
| P0 — bring-up | экспортёры snmp/ipmi/rapl, карта розеток, PTP, governor `performance`, кросс-валидация PDU↔RAPL↔IPMI | доверенный инструмент (общая с E0 SS-ветки) |
| P1 — калибровка модели мощности | ступенчатая загрузка узла (stress-ng, уровни утилизации 0→100 % с шагом ~10 %), фит K0/K1/K2 по PDU; отдельно замер idle и **погашенного** узла | NodePowerModel для Peaks + первые публикуемые числа (кривая ватт/утилизация R760, доля холостого хода) |
| P2 — сравнение политик | плечи: default / TargetLoadPacking / **Peaks** (LoadVariationRiskBalancing — как контроль класса load-aware), одинаковый поток задач (Geant4 + ML-инференс), уровни подачи: разреженный / средний / плотный | Дж/задача, EDP, средняя мощность кластера — парно по повторениям |
| P3 — полный цикл с гашением | лучшая политика P2 + гашение освобождённого узла по BMC (порог простоя), сравнение: без гашения / с гашением | главный партнёрский результат: экономия полного цикла в кВт·ч и ₽ |
| P4 (опция) — свип governor | performance / schedutil / powersave поверх победителя | взаимодействие DVFS с политикой размещения |

Предрегистрация до прогонов (как всегда): ожидаемая ошибка модели P(x) по
PDU (порог, %); ожидаемая Дж/задача-разность Peaks против default при
каждом уровне подачи; ожидаемая доля экономии, приходящаяся на гашение
(прогноз: **большая часть** — консолидация без гашения даёт мало).

### Угрозы валидности (называем сразу)

- **Гомогенный стенд из 3 узлов**: механизм «предпочесть эффективное железо»
  не проявится (K0/K1/K2 одинаковы) — Peaks здесь работает только выпуклостью
  кривой и консолидацией. Честно ограничить перенос; гетерогенность — при
  расширении парка партнёром.
- **Интерференция от уплотнения**: консолидация удлиняет makespan
  (конкуренция за LLC/память/диск) и может съесть выигрыш по ваттам — Дж/задача
  это поймает интегрально; в этой ветке эффект только констатируется как
  trade-off, без модели.
- Peaks смотрит на CPU-утилизацию: для IO/сетевых задач его прогноз мощности
  смещён — подача включает такие задачи, смещение будет видно в P2.
- 3 узла — минимальный размер для консолидации (2 активных + 1 погашен);
  выводы о масштабировании — только качественные.
- Гашение/подъём узла не бесплатны (время загрузки, износ): учесть цену
  перехода в модели порога простоя.

## 2. Сценарии использования (партнёрская рамка)

| # | Сценарий | Ценность | Чем подтверждается |
|---|---|---|---|
| U1 | **Консолидация + гашение простаивающих узлов** (Peaks + BMC) | прямые кВт·ч: не платить за холостой ход (30–60 % пика) | P1 (доля холостого хода) + P3 |
| U2 | **Энергоучёт на задачу**: Дж/задача, Дж/инференс — чарджбек, тендеры | измеренная себестоимость вычисления | P2 (PDU-истина) |
| U3 | **Тарифные окна и пик мощности**: гибкие серии в ночной тариф, срезание пиков (Peaks минимизирует скачок мощности по построению) | деньги без нового железа | регистры PDU + Д8 |
| U4 | **TCO/CO₂-отчёт**: кВт·ч/год, ₽/год, кг CO₂e/год | одностраничник + дашборд | модель из P2/P3 |
| U5 | (перспектива) гетерогенный парк: авто-предпочтение эффективного железа | продление жизни старых серверов | при расширении парка |

## 4. Обзор существующих решений (каркас related work)

Позиции — навигация; перед вставкой в статью верифицировать по Crossref,
как в статье №1.

1. **Энергоосознанные планировщики оркестраторов** — ядро обзора:
   Trimaran **Peaks** (наш предмет; модель и код разобраны), KEIDS
   (Kubernetes-based energy+interference driven scheduler, IEEE IoT J. —
   проверить), энергоориентированный co-scheduling в HPC (Zheng, Papka,
   Lan — [22] статьи №1), RL-co-scheduler [21].
2. **Упаковка + гашение**: MostAllocated / RequestedToCapacityRatio,
   TargetLoadPacking; Cluster Autoscaler / Karpenter consolidation (в облаке;
   на bare-metal аналога гашения «из коробки» нет — наш P3 закрывает это
   BMC-сценарием), Descheduler HighNodeUtilization, KEDA scale-to-zero.
3. **Измерение энергии**: Kepler (eBPF+RAPL+модель, per-pod оценка),
   Scaphandre, энергоучёт Slurm; классика несоразмерности энергии нагрузке
   (Barroso & Hölzle, energy proportionality) — обоснование U1.
4. **HPC power management**: Slurm powersave / power capping, EAR (BSC),
   GEOPM (Intel); литература race-to-idle vs DVFS — фон для P4.
5. **Carbon-aware**: линия Google Carbon-Intelligent Computing, carbon-aware
   KEDA, свежий обзор arXiv 2508.05949 (2026). В статье — как контекст;
   для российского ДЦ практичнее тарифные окна и пик (U3), CO₂ — диапазоном.

**Разрыв, на который встаёт статья:** энергоосознанные планировщики K8s
существуют как код, но не как измеренная практика — нет воспроизводимой
калибровки моделей мощности на современном bare-metal, нет наземных (PDU)
оценок экономии, нет разделения «сколько даёт размещение само по себе и
сколько — гашение». Ровно это закрывают P1–P3.

1. До прода: чек-лист Д1–Д8 (с power control в Д4) партнёру; журнал — с

образуют мост к интерференционному направлению — возможная совместная
