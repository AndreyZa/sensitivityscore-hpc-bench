# Metal3 как исполнитель гашения (разбор для Ш8/P3)

Дата разбора: 20.08.2026. Вопрос: чем исполнять гашение узлов в P3 —
самописным Redfish-скриптом (механика проверена руками в Э1.4) или
Metal3. Факты сверены с book.metal3.io (bmo/externally_provisioned,
bmo/state_machine) 20.08.2026.

## Что такое

Metal3 = baremetal-operator (BMO) + Ironic: CRD `BareMetalHost` (BMH)
описывает физический сервер с BMC-адресом и Secret'ом кредов; BMO через
Ironic исполняет декларируемое состояние. Обычное назначение — полный
провижининг (PXE, образы), но есть режим ровно под наш случай:

**`spec.externallyProvisioned: true`** — узел «установлен третьей
стороной»: ни инспекции, ни чистки, ни переливки ОС; BMO управляет
ТОЛЬКО питанием (`spec.online: true/false`) и ребутом
(reboot-аннотация). Наши узлы уже стоят под k0s — это оно.

## Как ложится на стенд

- BMO + Ironic — на ss-system VM (не на bench-узлах); Ironic в
  power-only-роли: без dnsmasq/PXE, sqlite-бэкенд.
- 3 × BMH (wrk-b6/b7/b8) с `externallyProvisioned: true`,
  `automatedCleaningMode: disabled` (страховка: даже при ошибочном
  выходе из externally-provisioned Ironic не потрёт диски),
  `bmc.address: idrac-virtualmedia://10.21.200.10X` + Secret с кредами
  (та же секрет-практика, что snmp/idrac-poller; в git не попадает).
- Сеть: ss-system уже ходит в 10.21.200.0/24 (idrac-poller) — доступ есть.
- **Политика остаётся нашей**: Metal3 не знает про простой и очереди.
  Контроллер-аналог power_save (порог T, наблюдение за очередью,
  cordon/uncordon) пишем в любом случае; Metal3 заменяет только
  исполнительный слой — вместо вызова Redfish контроллер выставляет
  `spec.online`, а ретраи/статус/идемпотентность несёт BMO.

## За и против

За: декларативное целевое состояние вместо императивных вызовов; статус
и ошибки в API кластера; стандартный компонент экосистемы — для статьи
это усиление тезиса «штатными средствами» (§1, вклад 1) и честный ответ
рецензенту «а не самоделка ли ваш power_save». Против: Ironic — заметная
зависимость (контейнеры + БД) на проде посреди измерительной кампании;
ещё один слой отказа между политикой и BMC; выход из
externally-provisioned не поддерживается (для нас некритично — нам из
него выходить незачем).

## Решение (предложение)

Двухслойный дизайн: политика одна, исполнитель за интерфейсом.

- Вариант А — Redfish напрямую (обкатан в Э1.4: Off за 18 с, Ready за
  2:59). Минимум движущихся частей; на нём гоним Ш8 — в измерении не
  должен участвовать компонент, который сам ещё обкатывается.
- Вариант Б — `BMH.spec.online` через Metal3. Поднимаем на ss-system
  параллельно, валидируем цикл на wrk-b8 (повторить Э1.4-процедуру через
  spec.online, сверить тайминги). Если валиден до Ш8 — Ш8 измеряем на
  Б, и статья пишет «исполнитель — стандартный компонент Metal3»; если
  нет — Ш8 на А, Metal3 в статье остаётся упоминанием в §2 и работой
  продолжения.

Интерфейс контроллера: `power_executor = redfish | metal3` в конфиге,
обе ветки покрыты dry-run-тестами.

## Шаги (когда решим поднимать)

1. Манифесты BMO+Ironic (power-only) в k8s/energy/metal3/ + Secret'ы
   по образцу snmp-secret.
2. 3 × BMH externallyProvisioned + вычитка статусов.
3. Валидационный цикл на wrk-b8 (день, вне ночных окон): online false →
   сверка P_выкл по PDU/BMC → online true → Ready → uncordon.
4. Контроллер power_save: политика + два исполнителя + тесты.
