## 1. Платформа

**Железо:** 3× Dell PowerEdge R760 — 2× Intel Xeon Platinum 8462Y+
(Sapphire Rapids, 32 ядра/сокет, **2 NUMA-домена**), 384 ГБ RAM,
bare-metal. **SMT выключен в BIOS насовсем** → 64 ядра/узел. Диск —
один Dell BOSS-N1 447 ГБ (NVMe, Marvell 88NR2241), весь узел на нём:
`/` 438 ГБ, из них занято 18 ГБ. Сеть — bond0 из двух портов Broadcom
(`bnxt_en`, eno12399np0 + eno12409np1) в 802.3ad LACP, **2×10G = 20
Гбит/с** (снято с узлов 20.08.2026: `/sys/class/net/bond0/speed` = 20000
на всех трёх; ранее в этом разделе стояло «2×25G» — ошибка, никем не
измерявшаяся). Измеренный `NET_REFERENCE_MBPS=16718` с 20 Гбит/с
согласуется (84% линка), с 50 Гбит/с — нет; то есть калибровка сети
всё это время была верной, а подпись к ней — нет.
Следствия против STAGE: NUMA-ось активна (2 сокета); L3 socket-wide
(120 МБ/узел суммарно) — узловой датчик видит контраст сокета целиком; PMU
честный (без гипервизора); полные ядра (не 500m-квоты) — различение по
декларации S (β > 0) проверяемо; `G4_THREADS` high-s = 28–32 (ядра
NUMA-домена).

**Служебные ВМ** — 4× (4 vCPU / 8 ГБ / 100 ГБ SSD) на отдельном
гипервизор-хосте, **НЕ на R760** (фон etcd/CH исказил бы метрики bench):
3× control-plane (HA-кворум etcd; узкое место — fsync-латентность диска
etcd, p99 < 10 мс) + 1× ss-system (Redis, планировщик, metrics-server,
in-cluster ClickHouse; роль + taint).

**Версии (на вводе):** k0s v1.35.6 на всех узлах (порог Slinky K8s ≥ 1.35
пройден — остаётся Slurm ≥ 25.11); Ubuntu 24.04.4 LTS, ядро 6.8
(bench 6.8.0-138, ss-system -136).

**ОС и ядро — почему Ubuntu 24.04:** PSI включён по умолчанию (IO-ось
строится на `io.pressure`; Debian/RHEL требуют `psi=1`), cgroup v2 unified
(агент рассчитан на v2: `stat -fc %T /sys/fs/cgroup` → cgroup2fs), ядро
≥ 5.8 → `CAP_PERFMON`. Immutable-дистрибутивы отвергнуты: стенду нужно
узловое перф-ковыряние. `perf_event_paranoid`: с CAP_PERFMON дефолт `=2`
обычно достаточен — сначала perfcheck; если `FAILED to open` — закрепить
`kernel.perf_event_paranoid = 1` в `/etc/sysctl.d/99-perf.conf` (не `echo`
в /proc — живёт до ребута); paranoid=3 — downstream-хардненинг, может не
хватить и CAP_PERFMON.

**На будущее:** конфигурация B (KubeVirt) — vPMU passthrough под вопросом
(сбор host-side по cgroup qemu как приближение); GPU — ограничения
slurm-bridge по DRA-драйверам.

## 2. Диагностика узла (повторять на каждом новом)

**(а) PMU — cgroup-scoped `perf_event_open()`:**

```bash
make perfcheck-image && make perfcheck-push
make perfcheck-run NODE=<узел>   # по каждому типу узла, ДО агента
make perfcheck-logs              # SUCCESS + ненулевое число
make perfcheck-clean
```

`SUCCESS` + ненулевое = PMU честный; `WARNING ... exactly zero` — счётчик
открылся, но гипервизор подделывает; `FAILED to open` — права
(`EPERM` → sysctl §1; `EINVAL` — не среда: cgroup-события требуют
`cpu >= 0`, агент открывает по счётчику на CPU).

**(б) Сеть — cross-node полоса** (референс — не номинал NIC, из-под CNI он
не читается; same-node трафик мостится veth мимо физического NIC):

```bash
make netcheck-run && make netcheck-logs   # NET_REFERENCE_MBPS=<N>
make netcheck-clean
make netcheck-apply NET_REFERENCE_MBPS=<N>   # перезапускает агент — между сериями
```

Прогнать на нескольких парах: полоса бывает неоднородна (на STAGE
900–1335 Мбит/с между «одинаковыми» узлами).

## 4. Канал оповещений (проверить до первой длинной серии)

Смысл: правила описывают состояния, в которых стенд **продолжает писать
цифры, но нести их в диссертацию уже нельзя** — а серия идёт 4 часа без
оператора. `make alerts-status` / `make alerts-test` (синтетический алерт —
в чат придёт сообщение и снятие). Сторож `SSWatchdog` обязан быть firing
(vector(1), два сообщения в сутки): молчание канала отличимо от здоровья.

- **Правила разделены меткой class**: `stand` (стенд сломан — агент встал,
  CH не принимает, etcd без лидера) → в чат; `validity` («числа серии под
  вопросом» — срабатывают от самой нагрузки эксперимента) → в чат НЕ идут,
  видны на панели и попадают в завершающее уведомление серии
  (run-series.sh спрашивает Prometheus за окно прогона). Перезапуски и
  OOMKill в неймспейсе серии инцидентом не считаются вовсе — это исход
  эксперимента, харнесс пишет их сам.
- **Ловушка партнёрской сети:** `api.telegram.org` резолвится в
  `149.154.166.110`, который из сети стенда НЕ отвечает. Работает другой
  фронт Bot API — `149.154.167.220`: под ss-notifier получает `hostAliases`
  (подменяется имя, не адрес — иначе сломался бы SNI). Хрупко, запасного
  адреса нет; если встанет — `SSAlertDeliveryFailing` на панели, лечить по
  возрастанию: живой фронт → `SS_NOTIFY_BACKEND=ntfy` → просить партнёра
  открыть адрес.
- **ss-notifier живёт в прод-кластере** (не на лабе): маршрута
  кластер→лаба нет (WG поднимает лаба, обратно не маршрутизируется), а
  обратный туннель поставил бы оповещения в зависимость от моргающего
  Wi-Fi. Чат меняется `make notifier-chat CHAT_ID=…` (Secret + рестарт);
  ловушка: при превращении группы в супергруппу chat_id меняется на
  `-100…` и бот молкнет молча — ловит сторож.
- **Уведомления о серии** идут через проброс `ss-forward@ss-notifier` на
  .72 (`notify()` шлёт на 127.0.0.1:8790 и при мёртвом адресе молчит по
  построению); с 19.08 канал проверяет preflight серии.

## 7. Смоук и цены осей (исполнено 18–19.08.2026)

**Смоук** (`STAND=prod make series SERIES=smoke PILOT=1`): 36 строк, rc=0;
PMU 1.000×3. Нюансы: `PILOT=1` гоняет ТОЛЬКО pressure-пилот (BASELINE в
логе не будет — эталоны догнаны отдельно); задача 5M primaries на SPR ≈
19 с — дозу смоука задним числом не менять, рабочим сериям закладывать
PRIMARIES ≈ 60–75M (~4–5 мин).

**Цены осей — ступень закрыта в два захода, веса применены 19.08:**
- *Заход 1* (обращение скор-функции — путь STAGE): все α/β ≈ 0, R²=0.04.
  Причины: high-s кэш-резидентна на 120 МБ LLC (шторм её не задевает);
  PSI io в моменты решения пульсирует около нуля; high-s-net номинальна.
- *Заход 2* (давления за ИНТЕРВАЛ задачи из Prometheus,
  `calibrate_axis_costs.py --prometheus-url`; по дороге найден и починен
  сдвиг таймстампов −3ч в CH): **R²=0.64, клетка io×io предсказана
  0.068/0.068**. Цены: **β_io=1.31 [1.02; 1.59]**, α_llc=0.014,
  α_net=0.009, β_llc=β_net=0 (честные нули текущих жертв), γ=0.003.
  Урок в Методике: давления в фит — за интервал задачи, не по снапшотам
  решения.

Веса в `config-prod-base.yaml` + ConfigMap; серии с этого момента НЕ
разведочные. Рекалибровка v2 (ML-жертва по membw, stream + egress-шторм,
NUMA-шторм) поднимет нулевые цены. Регрет: SS значимо лучше default
(Holm p 0.01–0.03).

**После каждой серии:** `make ch-load-all STAND=prod RUN_LABEL=… …`
(dual-write: упавший приёмник называется с командой долива) + энергия окон
`./scripts/energy-windows-from-log.sh <лог> <стенд> <label>` + отчёт
`make ch-analyze`. Раз в неделю и перед работами на .72: `make ch-backup`
(архив верифицируется восстановлением сам), копию в облако.

## 10. A5-прогноз: PMU-мультиплексирование (предрегистрация, ЗАКРЫТ)

Перенесено дословно из «A5-прогноз (прод).md» 19.08.2026 при объединении
документов. **Зарегистрирован 20.07.2026, коммит `c19a721` — ДО первой
прод-серии**; полный вывод с методикой замера — «Аудит и план работ.md» §A5.
Идёт в диссертацию как пример предрегистрации.

**Прогноз** (для R760, 8462Y+): архитектурный PMU Intel даёт 8
программируемых счётчиков на ядро; при SMT — 4 на логический CPU, ровно под
конфигурацию агента (LLC-пара + NUMA-пара = 4 события на под).

1. `ss_agent_pmu_multiplex_ratio` = 1.000 на bench-узлах под серией — при
   любом числе подов, пока PMU не пользуется никто, кроме агента.
2. **Пятое событие на под стоит трети окна** (~0.67): любая добавка —
   третья ось на core-PMU, параллельный `perf`, Intel PCM, профилировщик —
   роняет долю в зону, где выводам по `llc_*` верить нельзя. ⟵ это правило
   действует и после закрытия прогноза.
3. Если SMT выключат — 8 счётчиков на поток, запас на одну лишнюю пару.

Основание: плотность узла на мультиплексирование не влияет (cgroup-событие
простаивающего пода счётчик не занимает; соперничают только события одного
пода). **Опровержение**: доля окна < 0.99 на спокойном узле, где работает
только агент, — означало бы < 4 счётчиков, и ДО серий пришлось бы либо
отказаться от NUMA-пары, либо перейти на узловые (не-cgroup) счётчики.

**Статус — закрыт полностью:**
- 18.08.2026, разведка: SMT выключен в BIOS → активна ветка 3 (8 счётчиков
  на поток, запас на лишнюю пару); 19.08 SMT off принят как постоянная
  конфигурация стенда — ветка 3 зафиксирована насовсем, дозы жертв
  28 CPU/28 потоков.
- [x] 18.08.2026, perfcheck: `PMU multiplex ratio = 1.000`
  (enabled==running до наносекунды) на wrk-b6, b7, b8.
