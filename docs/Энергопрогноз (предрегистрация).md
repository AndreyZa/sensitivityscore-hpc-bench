# Энергопрогноз — предрегистрация чисел (ЗАМОРОЖЕНО 18.08.2026)

Составлен 17.08.2026 для энерговетки ([[Энергоэффективность — статья (план)]],
фазы P0–P3). Образец — [[A5-прогноз (прод)]]: числа фиксируются коммитом **до
первого прогона фазы P0 на проде**; до этого момента черновик можно править,
после — изменения только дописыванием новой записи с датой и обоснованием,
задним числом ничего не меняется.

Статус: **ЗАМОРОЖЕНО 18.08.2026** (коммит этой правки — регистрация; дальше
только дописывание с датой). Исходные числа предложены 17.08 до контакта с
железом (паспортные данные R760/8462Y+, SPECpower-профили двухсокетных
серверов); при заморозке учтена разведка 18.08 (раздел «Уточнения» ниже).
Решения заморозки: Э1.1 сужен по разведке и помечен НЕслепым; Э1.2 оставлен
слепым; добавлен порядковый критерий Э0.4 (psys); E5 плана переформулирован
под смену BIOS-профиля (cpufreq в ОС нет).

Правило чтения: каждый прогноз — интервал; попадание = подтверждение, промах =
не «ошибка», а результат, который обязан попасть в статью с объяснением.

## P0 — доверие инструменту (кросс-валидация источников)

| # | Величина | Прогноз | Критерий проверки |
|---|---|---|---|
| Э0.1 | Согласие PDU ↔ IPMI DCMI, средняя мощность на стационарной нагрузке, окно ≥ 10 мин | расхождение **≤ 8 %** от показания PDU | на трёх уровнях: idle, ~50 %, полная CPU-нагрузка |
| Э0.2 | Σ RAPL (2×package + DRAM) относительно розетки PDU | **50–85 %** под полной CPU-нагрузкой; **35–65 %** на холостом ходу | RAPL не видит вентиляторы, диски, NIC, VRM/потери PSU — доля обязана быть < 1 всегда; нарушение Σ RAPL > PDU = недоверие инструменту, стоп до выяснения |
| Э0.3 | Дрейф показаний PDU на выключенной нагрузке (стабильность регистра) | накопление **≤ 0,5 %** энергии окна за часовое окно простоя | защита от шума младших разрядов регистра |
| Э0.4 | Порядок источников на узле и окне | **Σ RAPL(package+dram) ≤ psys ≤ PDU** — строгая цепочка на каждом узле в каждом окне P0 | добавлен при заморозке 18.08 (на узлах есть psys-домен): psys покрывает платформу шире сокетов, но меньше розетки (потери PSU, вентиляторы). Числовой вилки нет — отношение psys/PDU записывается как измеренное. Нарушение цепочки = недоверие инструменту, стоп до выяснения |

## P1 — калибровка модели мощности узла (Dell R760, 2× Xeon 8462Y+, 384 ГБ)

| # | Величина | Прогноз | Примечание |
|---|---|---|---|
| Э1.1 | Мощность холостого хода узла (частоты — BIOS-профиль Performance, без задач) | **220–320 Вт** | сужен при заморозке 18.08 по разведке (iDRAC: 236–268 Вт на почти пустых узлах) — прогноз **НЕ слепой** и предрегистрационной силы не имеет, в статье им не козырять; слепыми остаются Э1.5 и все Э2.x/Э3.x |
| Э1.2 | Пиковая мощность под полной CPU-нагрузкой (stress-ng, все ядра) | **850–1150 Вт** | 2× TDP 350 Вт + платформа |
| Э1.3 | Доля холостого хода от пика | **25–45 %** | ядро аргумента U1: «упаковка без гашения почти не экономит» |
| Э1.4 | Мощность погашенного узла (BMC power off, розетка под напряжением) | **10–40 Вт** | BMC + дежурное питание PSU |
| Э1.5 | **Форма кривой P(x)** | вогнутая, насыщающаяся (наибольший прирост ватт — на низкой утилизации, как в SPECpower-профилях); в параметризации K0 + K1·e^(K2·x) это **K1 < 0 и K2 < 0** | следствие, регистрируемое как предсказание поведения: на вогнутой модели минимальный «скачок мощности» — у уже нагруженного узла, то есть **Peaks будет уплотнять**; если кривая выйдет выпуклой — Peaks будет разносить, и это меняет интерпретацию всей P2 |
| Э1.6 | Качество фита | RMSE **≤ 5 %** пиковой мощности на удержанных ступенях (fit по чётным ступеням, проверка по нечётным) | ступени утилизации 0→100 % с шагом 10 %, по PDU |
| Э1.7 | Разброс между тремя узлами (номинально одинаковыми) | idle и пик совпадают в пределах **± 7 %** | больший разброс = неоднородность парка, отдельная строка в статью и по-узловые модели обязательны |

## P2 — сравнение политик (default / packing / peaks; поток Geant4)

Плечи получают идентичный поток; уровни подачи: разреженный (~⅓ ёмкости),
средний (~⅔), плотный (насыщение). Гашения узлов в P2 НЕТ — измеряется
чистый эффект размещения.

| # | Величина | Прогноз | Примечание |
|---|---|---|---|
| Э2.1 | Разность Дж/задача между политиками **без гашения** | **≤ 7 %** между любой парой плеч на всех уровнях подачи | это «нулевой» прогноз-провокация: пока все узлы включены, холостой ход платится всюду, и выбор узла двигает только рабочую точку кривой. Опровержение (кто-то выиграл > 7 %) — самый интересный исход |
| Э2.2 | Интерференционный штраф уплотнения | на плотной подаче среднее время задачи у packing **на 5–15 % выше**, чем у default | полные ядра, 2 NUMA-домена: соседство по сокету не бесплатно. Дж/задача ловит это интегрально: дольше считаем — дольше жжём |
| Э2.3 | Поведение Peaks при вогнутой модели (условно к Э1.5) | размещения Peaks совпадают с packing в **≥ 70 %** решений | при выпуклой модели прогноз зеркальный: совпадение с default-разносом |
| Э2.4 | EDP | лучшая политика по Дж/задача ≠ лучшая по EDP хотя бы на одном уровне подачи | фиксируем, что компромисс время↔энергия существует и виден прибором |

## P3 — полный цикл с гашением (главный партнёрский результат)

Сценарий: разреженная подача (~⅓ ёмкости), политика-победитель P2 +
гашение простаивающего узла по BMC против default без гашения.

| # | Величина | Прогноз | Примечание |
|---|---|---|---|
| Э3.1 | Снижение энергии на задачу полного цикла | **25–50 %** против default-без-гашения | арифметика: 2 узла из 3 уходят с Э1.1 (сотни ватт) на Э1.4 (десятки) |
| Э3.2 | Доля экономии, приходящаяся на гашение (а не на выбор рабочей точки) | **≥ 80 %** | центральный тезис ветки в одном числе |
| Э3.3 | Цена перехода | цикл drain → power off → power on → Ready **≤ 15 мин** на узел; энергия цикла включения **≤ 3 %** экономии часового окна простоя | определяет минимальное окно простоя, при котором гашение окупается — это число идёт партнёру в модель порога |

## Что считается фальсификацией ветки

Не промах отдельного интервала, а: (а) Σ RAPL > PDU или несходимость
PDU↔IPMI хуже 15 % — инструменту нет доверия, публикуемых чисел нет;
(б) Э3.1 < 10 % — «полный цикл» не даёт партнёрски значимой экономии, статья
переформулируется от экономии к измерительной методике и честному
отрицательному результату.

## Уточнения по разведке железа (18.08.2026, до заморозки)

Черновик ещё не заморожен — эти факты законно уточняют вилки; после
заморозки такой раздел мог бы только дописываться.

- **SMT выключен в BIOS** (64 ядра, 1 поток/ядро; см. A5-прогноз, ветка 3).
  К обсуждению Э1.2: пиковая мощность прогнозировалась до этого знания;
  полная CPU-нагрузка без SMT грузит те же физядра, вилку 850–1150 Вт
  пока не двигаем, но помнить при разборе промаха.
- **RAPL на bench: 5 зон, включая psys** (2× package + 2× dram + psys;
  снимает metrics-agent — `ss_node_rapl_joules_total`, см.
  k8s/monitoring/energy/README.md). Для Э0.2 появляется дополнительная
  внутренняя сверка: Σ(package+dram) ≤ psys ≤ PDU — psys покрывает
  платформу шире сокетов, но меньше розетки (PSU-потери, вентиляторы).
  Ориентир на холостом: package-0 ≈ 49 Вт.
- **iDRAC (Redfish 1.20.1): накопительного счётчика энергии НЕТ** —
  только мгновенная мощность (+min/avg/max за 1 мин). Источник ipmi в
  energy_windows будет интегрированием опроса ~1 Гц, а не разностью
  регистра; Э0.1 это не меняет (сформулирован по средней мощности),
  но точность источника ipmi ограничена частотой опроса — регистры
  остаются у PDU (кВт·ч) и RAPL (джоули). Мгновенная мощность узлов
  под лёгкой нагрузкой ОС: 245–268 Вт — нижняя половина вилки Э1.1
  выглядит правдоподобной.
- **PSU: активен PS1, PS2 в горячем резерве ~5 Вт** — карта розеток
  обязана суммировать обе розетки узла (уже было в плане §3, теперь
  подтверждено показаниями PSU-сенсоров).
- **cpufreq-драйвера в ОС нет** (частоты держит BIOS-профиль
  Performance): фикс governor для P1–P3 выполнен «by construction».
  Решено при заморозке 18.08: E5 в плане переформулирован — вместо
  свипа governor'ов ОС свип **профилей питания BIOS** через
  партнёра/iDRAC (опционально, при их поддержке; см. план §5).

## Порядок заморозки

1. Обсудить вилки (особенно Э1.1/Э1.2 — они каскадом задают Э1.3 и Э3.1).
2. При необходимости поправить ДО первого прогона P0.
3. Коммит с пометкой «ЗАМОРОЖЕНО» в заголовке + дата — регистрация;
   дальше только дописывание.
